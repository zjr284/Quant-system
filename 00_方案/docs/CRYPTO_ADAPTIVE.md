# AI adaptive strategy selection (Spot Testnet only)

## Safety boundary

`quant crypto adaptive-run` defaults to `--mode shadow`. Shadow mode consumes only
public Spot Testnet BTCUSDT/ETHUSDT closed hourly candles and sends derived market
features to an HTTPS OpenAI-compatible API. It has no Binance account client and
cannot submit/cancel orders. The prompt contains no exchange credentials.
The provider request uses JSON Object mode for compatibility with DeepSeek Chat
Completions. The application validates the exact response fields and profile
allowlist locally; malformed or unknown output is rejected and cannot switch the
active profile.

The model may return only `sma_24_72` or `cash`. The first is the existing fixed
SMA24/72 long/cash rule, capped by the executor at 25% per symbol and 50% total;
the second targets cash. The deterministic executor retains all order limits,
precision checks, daily loss lock, symbol allowlist and IOC price protection.
The AI cannot change any of these settings.

Every hourly input, canonical input hash, model version, validated response,
failure, candidate count, active profile, transition, risk check and order receipt
is recorded in SQLite. A new profile needs three consecutive hourly evaluations
and the current profile must have been active for at least 24 hours. Invalid
responses, API failures and stale data never change the active profile. They are
journaled and optionally sent to `QUANT_ALERT_WEBHOOK_URL`.
Process restarts also clear a pending confirmation streak.

## Server: start with shadow observation

1. Install this archive over `/opt/quant`, install the existing crypto dependencies,
   then run `sudo bash /opt/quant/deploy/tencent/install-adaptive-shadow.sh`.
2. Stop the previous fixed-strategy Testnet executor before starting shadow mode;
   do not run both services against the same account at once:

   ```bash
   sudo systemctl disable --now quant-testnet
   sudo install -o root -g root -m 0600 /dev/null /etc/quant-ai.env
   sudo nano /etc/quant-ai.env
   ```

3. Set only the AI connection values in `/etc/quant-ai.env`:

   ```text
   QUANT_AI_BASE_URL=https://YOUR_PROVIDER/v1
   QUANT_AI_API_KEY=YOUR_AI_KEY
   QUANT_AI_MODEL=YOUR_MODEL_ID
   ```

   Keep the file `root:root`, mode `0600`. Do not put Binance keys in this file.
   For external alerts, create `/etc/quant-alert.env` as `root:root`, mode `0600`,
   with `QUANT_ALERT_WEBHOOK_URL=https://YOUR_PRIVATE_WEBHOOK`. Start the no-order observer:

   ```bash
   sudo systemctl enable --now quant-adaptive-shadow
   sudo systemctl status quant-adaptive-shadow --no-pager
   sudo journalctl -u quant-adaptive-shadow -f
   sudo -u quant-adaptive /opt/quant-venv/bin/quant crypto adaptive-status \
     --db /var/lib/quant-adaptive/adaptive.sqlite
   ```

4. Keep shadow mode running for 30 consecutive days. Review hourly feature hashes,
   model versions, errors, regime choices, transition candidates and outages. Any
   missing hour or unexplained journal difference restarts the observation gate.
   `adaptive-status` reports accepted-hour count, observation span and missing or
   failed hours; require at least 720 consecutive accepted hourly decisions for
   the 30-day gate.

## Manual acceptance gate before Testnet auto mode

Use `quant crypto adaptive-backtest --btc-csv ... --eth-csv ...` to compare the
two compiled profiles. It records three chronological slices, fees, slippage,
order caps, daily-loss lock, deterministic IOC non-fill and partial-fill scenarios,
risk-adjusted return, drawdown and turnover. Vary fill assumptions and retain the
output with the frozen input files. This historical profile comparison does not
simulate what the AI would have chosen in the past; review the recorded shadow
recommendations separately and do not claim the comparison validates AI skill.

The acceptance file is a human-reviewed record, not proof generated by the AI.
It must document independently checked cost-aware, staged backtests and Testnet
order/restart/reconciliation evidence, plus a review of the actual 30-day shadow
recommendation history. Fill in `approval_id` only after review.
The CLI refuses Testnet auto mode unless every gate is explicitly true and exactly
the two compiled profiles are approved. The initial template fails closed:

```json
{
  "observation_30_days_passed": false,
  "backtest_costs_and_stages_passed": false,
  "shadow_decisions_replay_reviewed": false,
  "testnet_lifecycle_acceptance_passed": false,
  "reconciliation_passed": false,
  "human_approval": false,
  "approved_profiles": ["sma_24_72", "cash"],
  "approval_id": ""
}
```

Only after reviewing the evidence should an operator write the approved file to
`/etc/quant-adaptive-acceptance.json` as `root:quant-adaptive`, mode `0640` (the
service needs read access; the file contains no credentials). Create
`/etc/quant-adaptive-testnet.env` with `sudo install -o root -g root -m 0600 /dev/null /etc/quant-adaptive-testnet.env`;
put the Testnet API key/secret and AI settings there, never mainnet credentials.
Then stop shadow and explicitly enable
the separate Testnet-only order service:

```bash
sudo systemctl disable --now quant-adaptive-shadow
sudo systemctl enable --now quant-adaptive-testnet
sudo systemctl status quant-adaptive-testnet --no-pager
sudo journalctl -u quant-adaptive-testnet -f
sudo -u quant-adaptive /opt/quant-venv/bin/quant crypto adaptive-status
```

Do not edit the unit limits to increase risk. To stop new orders immediately:

```bash
sudo systemctl disable --now quant-adaptive-testnet
```

That stop writes a persistent `manual_shutdown` lock. Do not simply start the
service again. First inspect the Testnet account and open orders; then, while the
service is stopped, explicitly reset only that manual lock:

```bash
sudo bash -c 'set -a; . /etc/quant-adaptive-testnet.env; set +a; exec runuser -u quant-adaptive --preserve-environment -- /opt/quant-venv/bin/quant crypto testnet-unlock --db /var/lib/quant-adaptive/testnet.sqlite --confirm-manual-reset I_REVIEWED_TESTNET_ACCOUNT_AND_OPEN_ORDERS'
sudo systemctl enable --now quant-adaptive-testnet
```

The reset checks Binance Testnet account access and refuses if any open order is
present. A `daily_loss_limit` lock has a separate explicit human-review path; after
stopping the service and reviewing the loss, balance, fills, and open orders, run:

```bash
sudo bash -c 'set -a; . /etc/quant-adaptive-testnet.env; set +a; exec runuser -u quant-adaptive --preserve-environment -- /opt/quant-venv/bin/quant crypto testnet-unlock --db /var/lib/quant-adaptive/testnet.sqlite --confirm-daily-loss-review I_REVIEWED_DAILY_LOSS_AND_TESTNET_ACCOUNT'
```

It refuses if open orders exist or account reads fail, then resets the current
day's loss baseline to reconciled equity. Other lock reasons cannot be cleared by
these commands; investigate those and reconcile the account first.

This phase has no mainnet order adapter. Strategy additions, changed parameters,
live trading and eligibility for any account/region are out of scope.
